# Практическая работа № 8 — ролевая авторизация заявок

Версия `v0.8`. Сквозной проект «Система мониторинга параметров
микроклимата», индивидуальный вариант 17.

## Назначение и измененные компоненты

Добавлены:

- `app/authorization.py` — миграция структуры, правила RBAC и объектные
  проверки с безопасным отказом;
- `tests/test_authorization.py` — 20 базовых сценариев методички,
  12 индивидуальных и 14 дополнительных/интеграционных проверок;
- `demo_v08.py` — демонстрация с реальной аутентификацией `AuthService`,
  SQLite и входной валидацией.

Код практических № 1–7 не изменен. Прототип прав для **записей мониторинга**
в `app/security/access_control.py` сохранен отдельно от полномочий на
**заявки** в `app/authorization.py`: это разные предметные операции.

## Матрица доступа

| Операция | user | operator | admin | specialist |
| --- | --- | --- | --- | --- |
| `request.create` | Создает свою заявку | Нет | Нет | Нет |
| `request.read` | Только свою | Любую учебную | Нет | Нет |
| `request.close` | Нет | Только новую | Нет | Нет |
| `role.assign` | Нет | Нет | Другим обычным пользователям | Нет |
| `request.change_priority` | Нет | Нет | Нет | Новая заявка своего подразделения |
| Неизвестное действие | Нет | Нет | Нет | Нет |

Роль `specialist` получает только разрешение `request.change_priority`.
Она не наследует права оператора или администратора. Через `role.assign`
нельзя назначить `admin`, изменить административную учетную запись или
повысить собственные полномочия. Администратор может назначать и отзывать
`specialist`, `operator`, `user` у обычных пользователей.

## Достоверный источник атрибутов

1. `user_id` поступает исключительно из `AuthService.resolve(token)`, который
   проверяет срок и отзыв **реального** серверного сеанса v0.7.
2. Текущие `role`, `active` и `department_id` читаются из таблицы `users`
   при каждом защищенном обращении.
3. `owner_id` новой заявки устанавливается равным подтвержденному `user_id`.
   Клиент не задает владельца и подразделение новой заявки.
4. `status`, `owner_id` и `department_id` существующей заявки читаются из
   таблицы `requests`, а не из входного сообщения.
5. Неизвестные поля JSON, включая `owner_id`, `role`, `active` и
   `department_id`, отклоняются входной валидацией v0.5.

Последовательность: проверить реальный сеанс → начать `BEGIN IMMEDIATE` →
прочитать актуальные полномочия → проверить действие → проверить объект →
выполнить SQL либо откатить транзакцию. Сеанс проверяется до начала
транзакции, поскольку `AuthService.resolve()` сам открывает соединение к БД.
Одна операция `AccessService` использует выделенное SQLite-соединение, не
имеющее внешней незавершенной транзакции.

## Адаптация реальных схем v0.6/v0.7

`AuthService.initialize()` создает `users`, `sessions` с солью, хешами,
счетчиком блокировки и датами сеансов; `RequestRepository.initialize()`
создает `requests` со всеми ранее предусмотренными полями, включая вложения.
Оба инициализатора должны получить **один и тот же путь** SQLite-файла.
Затем `initialize_authorization()` безопасно добавляет недостающие столбцы:

| Таблица | Новые поля | Правило |
| --- | --- | --- |
| `users` | `role`, `department_id` | Старые пользователи получают минимальную роль `user` |
| `requests` | `owner_id`, `department_id`, `status` | Старые заявки сохраняются, неизвестный владелец/подразделение остаются `NULL`; статус `new` |

Миграция не удаляет таблицы, старые поля, пароли, сессии или вложения,
повторный вызов допустим. Для старых записей без владельца право `user` на
чтение не выдается. Пустое подразделение не считается совпадением и не
разрешает действие специалиста. При существующих реальных данных назначение
владельцев и подразделений потребует отдельно подтвержденной информации;
автоматически назначать их произвольному пользователю нельзя.

Демонстрация использует временную общую БД, но **те же классы и таблицы**,
что используются в проекте. Роль `admin` и подразделения в демонстрации
проставляются доверенной процедурой подготовки синтетического стенда;
открытая регистрация всегда назначает роль `user`.

## Индивидуальный вариант 17

Дополнительная операция — изменить приоритет заявки в состоянии `new`.
Область Б — заявки того подразделения, которому принадлежит специалист.
Сравниваются только серверные поля `users.department_id` и
`requests.department_id`. Приоритет целочисленный в пределах 1–5, как в
работе v0.6. Изменение происходит одним параметризованным `UPDATE` с
условиями по идентификатору, статусу и подразделению.

Если объект чужой, подразделение отсутствует, заявка закрыта или роль
отозвана, операция возвращает `AccessDenied`; приоритет и остальные данные
не изменяются. Запрос не может передать поддельное `department_id` отдельным
аргументом метода.

## Ответы на контрольные вопросы

**1. Почему действующий сеанс не разрешает читать любую заявку?**

Сеанс подтверждает пользователя, но не предоставляет все права. Доступ к
чтению определяется текущей ролью и, для `user`, совпадением `owner_id`
заявки с идентификатором пользователя.

**2. Чем `request.read` отличается от проверки владельца?**

`request.read` разрешает вид действия. Проверка владельца ограничивает
объекты. Оператор может читать все учебные заявки, а пользователь — только
собственные.

**3. Почему роль нельзя получать из клиентского поля `role`?**

Клиент может подделать его, например прислать `admin`. Поэтому роль
считывается из серверной БД после подтверждения сеанса. Неизвестные поля
JSON, включая `role`, дополнительно отклоняются валидатором.

**4. Почему администратор доступа не может читать заявки?**

В рамках этой политики администратор назначает роли. Чтение заявок не
требуется для выполнения этой функции. Разделение полномочий ограничивает
доступ к данным по принципу минимальных прав.

**5. Как проверяется изменение полномочий при прежнем сеансе?**

Администратор меняет роль в БД, пользователь обращается с тем же токеном,
а сервис повторно считывает его полномочия. Это проверено сценариями
№14, №25, №34 и №35.

**6. Чем отказ в авторизации отличается от недопустимого перехода состояния?**

При отказе нет прав на действие или объект. При недопустимом переходе
права есть, но состояние не допускает изменение. Например, оператор вправе
закрыть новую заявку, но повторно закрыть уже закрытую не может.

**7. Почему параметризованный SQL не предотвращает чтение чужого объекта?**

Параметризация отделяет значения от текста SQL и защищает от инъекции,
но запрос по чужому идентификатору остается синтаксически корректным.
Требуется отдельная серверная проверка владельца.

**8. Что потребуется при переходе к нескольким ролям пользователя?**

Понадобится связь «пользователь — роль» (например, таблица `user_roles`),
правила объединения разрешений и обработки конфликтов, отзыв отдельных
ролей и дополнительные тесты сочетаний. При каждом обращении сервис
должен вычислять актуальный набор полномочий.

## Ограничения

Это локальный учебный контур без сетевого API и реального потока показаний
датчиков. У пользователя одна текущая роль, наследования и полноценной
административной панели нет. SQLite `BEGIN IMMEDIATE` сериализует пишущие
операции и подходит для небольшого стенда, но ограничивает параллелизм.
Отзыв роли применяется к следующему обращению, а не прерывает уже начатую
операцию. Предусмотренные ранее прототипы аудита и проверки измерений не
являются промышленными механизмами защиты.
