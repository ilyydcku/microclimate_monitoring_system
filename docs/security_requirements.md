# Требования безопасности

## SEC-01

**Тип:** функциональное.

**Формулировка:** система должна отклонять доступ к данным мониторинга для неаутентифицированного пользователя.

**Связанные активы:** AS-01, AS-02, AS-07.

**Обоснование:** предотвращение несанкционированного получения данных мониторинга и сведений об источниках.

**Приоритет:** обязательное.

**Критерий приемки:** при обращении без подтвержденной учетной записи данные мониторинга не возвращаются.

**Способ проверки:** негативный интеграционный тест без аутентифицированного пользователя.

**Статус:** сформулировано.

## SEC-02

**Тип:** функциональное.

**Формулировка:** система должна предоставлять пользователю только операции, разрешенные его ролью в матрице доступа.

**Связанные активы:** AS-01, AS-03, AS-07.

**Обоснование:** ограничение действий пользователей в соответствии с назначенными полномочиями.

**Приоритет:** обязательное.

**Критерий приемки:** разрешенная операция выполняется, запрещенная операция отклоняется без изменения данных.

**Способ проверки:** позитивные и негативные тесты для ролей оператор, инженер и администратор.

**Статус:** сформулировано.

### Уточнение для версии v0.3

Проверка полномочий должна выполняться серверной частью для каждого защищенного запроса. Скрытие элемента интерфейса или клиентская проверка не считаются механизмом авторизации.

## SEC-03

**Тип:** функциональное.

**Формулировка:** только инженер с соответствующими полномочиями может изменять состояние записи мониторинга.

**Связанные активы:** AS-01, AS-07.

**Обоснование:** предотвращение неправомерного изменения состояния данных мониторинга.

**Приоритет:** обязательное.

**Критерий приемки:** инженер может изменить состояние разрешенной записи, а оператор и администратор не могут выполнить эту операцию.

**Способ проверки:** интеграционный тест с пользователями разных ролей.

**Статус:** сформулировано.

## SEC-04

**Тип:** функциональное.

**Формулировка:** система должна принимать показания только от зарегистрированного источника, подлинность которого подтверждена предусмотренной системой проверкой.

**Связанные активы:** AS-01, AS-02.

**Обоснование:** предотвращение попадания в систему показаний от неизвестного или подмененного источника.

**Приоритет:** обязательное.

**Критерий приемки:** данные от зарегистрированного источника с подтвержденной подлинностью принимаются, данные от неизвестного или не прошедшего проверку источника отклоняются и не сохраняются.

**Способ проверки:** позитивный тест с зарегистрированным источником и негативный тест с неизвестным идентификатором источника.

**Статус:** сформулировано.

## SEC-05

**Тип:** функциональное.

**Формулировка:** система не должна допускать изменение сохраненного значения показания через операции, которым такое изменение не разрешено.

**Связанные активы:** AS-01, AS-07.

**Обоснование:** защита целостности показаний микроклимата.

**Приоритет:** обязательное.

**Критерий приемки:** запрещенная попытка изменить значение измерения отклоняется, исходное значение остается неизменным.

**Способ проверки:** негативный интеграционный тест с последующей проверкой состояния записи.

**Статус:** сформулировано.

## SEC-06

**Тип:** функциональное.

**Формулировка:** административное изменение роли пользователя должно регистрироваться в журнале событий безопасности.

**Связанные активы:** AS-03, AS-04.

**Обоснование:** обеспечение контролируемости административных действий.

**Приоритет:** обязательное.

**Критерий приемки:** после изменения роли журнал содержит исполнителя, целевую учетную запись, время, прежнюю роль, новую роль и результат операции.

**Способ проверки:** интеграционный тест изменения роли и последующая проверка журнала.

**Статус:** сформулировано.

## SEC-07

**Тип:** функциональное.

**Формулировка:** при отсутствии обязательного секретного параметра приложение не должно переходить к нормальному режиму работы.

**Связанные активы:** AS-05, AS-08.

**Обоснование:** предотвращение запуска приложения с неполной защитной конфигурацией.

**Приоритет:** обязательное.

**Критерий приемки:** при отсутствии обязательного секретного параметра запуск завершается контролируемой ошибкой до начала обслуживания пользователей.

**Способ проверки:** запуск приложения в тестовом окружении без обязательного секретного параметра.

**Статус:** сформулировано.

## SEC-08

**Тип:** нефункциональное.

**Формулировка:** вывод приложения при предусмотренных сценариях запуска и ошибок не должен содержать значения секретных параметров.

**Связанные активы:** AS-05.

**Обоснование:** предотвращение раскрытия секретов через сообщения приложения.

**Приоритет:** обязательное.

**Критерий приемки:** значение секретного параметра отсутствует в стандартном выводе и сообщениях об ошибках при предусмотренных проверках.

**Способ проверки:** запуск приложения с тестовым секретом и анализ сформированного вывода.

**Статус:** сформулировано.

## SEC-09

**Тип:** нефункциональное.

**Формулировка:** после получения допустимого показания оно должно быть доступно для просмотра в учебной системе не позднее чем через 5 секунд на согласованном локальном стенде.

**Связанные активы:** AS-01, AS-08.

**Обоснование:** система мониторинга должна предоставлять актуальные данные без существенной задержки.

**Приоритет:** обязательное.

**Критерий приемки:** при 20 последовательных тестовых измерениях каждое принятое показание становится доступным для просмотра не более чем через 5 секунд после приема.

**Способ проверки:** измерение времени между приемом тестового показания и его доступностью для просмотра на локальном учебном стенде.

**Статус:** сформулировано.

## SEC-10

**Тип:** нефункциональное.

**Формулировка:** восстановление учебного сервиса мониторинга после отказа должно занимать не более 30 минут при наличии исправной подготовленной резервной копии и рабочего локального стенда.

**Связанные активы:** AS-01, AS-07, AS-08.

**Обоснование:** длительная недоступность системы нарушает основную функцию мониторинга.

**Приоритет:** обязательное.

**Критерий приемки:** на согласованном локальном стенде сервис восстанавливается и основные данные становятся доступны не более чем через 30 минут после начала процедуры восстановления.

**Способ проверки:** учебное испытание восстановления из подготовленной резервной копии с измерением времени.

**Статус:** сформулировано.

## SEC-11

**Тип:** процессное.

**Формулировка:** реальные секреты и локальный файл `.env` не должны включаться в отслеживаемое содержимое Git.

**Связанные активы:** AS-05, AS-06.

**Обоснование:** предотвращение публикации секретных параметров вместе с исходным кодом.

**Приоритет:** обязательное.

**Критерий приемки:** `.env` отсутствует среди отслеживаемых файлов Git, а в репозитории находится только безопасный шаблон `.env.example`.

**Способ проверки:** анализ `.gitignore`, `git ls-files` и содержимого подготовленных к коммиту файлов.

**Статус:** сформулировано.

## SEC-12

**Тип:** процессное.

**Формулировка:** изменения механизмов проверки полномочий, проверки источников данных и защиты целостности показаний до включения в основную версию должны проходить рецензирование и позитивные и негативные тесты.

**Связанные активы:** AS-01, AS-02, AS-03, AS-06.

**Обоснование:** снижение вероятности внесения ошибок в критичные механизмы безопасности.

**Приоритет:** обязательное.

**Критерий приемки:** для соответствующего изменения существуют результаты рецензирования и как минимум один позитивный и один негативный тест.

**Способ проверки:** анализ истории изменений, результатов тестирования и документации проекта.

**Статус:** сформулировано.

## SEC-13

**Тип:** функциональное.

**Формулировка:** система должна обнаруживать повторно переданные или устаревшие показания зарегистрированного источника и не принимать их как новое измерение. Для каждого источника сервер должен проверять уникальность сообщения по идентификатору/последовательности и допустимую свежесть временной метки.

**Связанные активы:** AS-01, AS-02, AS-07.

**Обоснование:** подтверждение подлинности источника само по себе не исключает повтор ранее допустимого сообщения.

**Приоритет:** обязательное.

**Критерий приемки:** первое допустимое сообщение сохраняется; повтор того же сообщения либо сообщение с уже использованным идентификатором/номером не создает новую запись. На учебном стенде сообщение с временной меткой старше 60 секунд относительно времени приема считается устаревшим. Значение 60 секунд выбрано как воспроизводимое учебное окно, существенно больше внутреннего требования SEC-09 о 5 секундах от приема до доступности показания; оно не является нормативом для реальных датчиков и подлежит пересмотру после выбора протокола и штатной частоты измерений.

**Способ проверки:** AT-07 с повторной передачей ранее принятого сообщения.

**Статус:** сформулировано, реализация запланирована.

## SEC-14

**Тип:** функциональное.

**Формулировка:** каждая успешная и отклоненная попытка изменения состояния записи мониторинга должна регистрироваться в журнале событий безопасности с указанием исполнителя, идентификатора записи, прежнего состояния, нового состояния, времени и результата операции.

**Связанные активы:** AS-04, AS-07.

**Обоснование:** необходимо обеспечивать прослеживаемость действий инженера и возможность установить автора изменения.

**Приоритет:** обязательное.

**Критерий приемки:** после успешной и отклоненной попытки изменения состояния в журнале присутствует событие с обязательными полями; значение измерения при этом не изменяется.

**Способ проверки:** AT-08.

**Статус:** сформулировано, реализация запланирована.

## SEC-15

**Тип:** нефункциональное.

**Формулировка:** точка приема показаний должна ограничивать размер одного запроса и частоту запросов от одного источника. Для учебного стенда принимаются значения: размер тела запроса не более 4 КиБ, устойчивый поток не более 10 запросов в секунду на источник с кратковременным пакетом до 20 запросов.

**Связанные активы:** AS-01, AS-08.

**Обоснование:** ограничения уменьшают вероятность исчерпания ресурсов одним источником. Значения 4 КиБ, 10 запросов/с и кратковременный пакет 20 запросов выбраны как воспроизводимые условия учебного стенда, а не как норматив для реальных датчиков. После определения протокола и штатной частоты измерений они должны быть пересмотрены.

**Приоритет:** обязательное.

**Критерий приемки:** запрос сверх размера отклоняется без сохранения данных; при превышении лимита частоты избыточные запросы отклоняются, а контрольный запрос допустимого источника и функция просмотра остаются доступными на учебном стенде.

**Способ проверки:** AT-09 на изолированном учебном стенде без проведения разрушительной нагрузочной атаки.

**Статус:** сформулировано, реализация запланирована.

## SEC-16

**Тип:** нефункциональное.

**Формулировка:** для учебного стенда хранилище журнала событий должно иметь отдельную квоту 100 МиБ и порог предупреждения 80 МиБ. При достижении 100 МиБ операции, которые по требованиям обязаны создавать событие аудита, должны отклоняться контролируемо до освобождения места; чтение показаний мониторинга не должно прекращаться. Уже сохраненные события не должны автоматически изменяться или удаляться.

**Связанные активы:** AS-04, AS-08.

**Обоснование:** неограниченный рост журнала способен исчерпать доступное хранилище. 100 МиБ выбрано как ограниченная учебная квота, достаточная для воспроизведения порогового поведения без значительного потребления диска.

**Приоритет:** обязательное.

**Критерий приемки:** при достижении 80 МиБ формируется предупреждение; при заполнении квоты изменение роли или состояния записи, требующее аудита, отклоняется без изменения прикладных данных; просмотр ранее сохраненных показаний остается доступным; существующие события журнала не изменяются.

**Способ проверки:** AT-10 на изолированном стенде с искусственно подготовленным объемом журнала.

**Статус:** сформулировано, реализация запланирована.

## SEC-17

**Тип:** функциональное.

**Формулировка:** после блокировки учетной записи или изменения роли сервер должен применять новые полномочия к уже существующему сеансу не позднее следующего защищенного запроса; старые полномочия не должны сохраняться до естественного завершения сеанса.

**Связанные активы:** AS-03, AS-01, AS-07.

**Обоснование:** иначе пользователь может продолжать выполнять действия с уже отозванными полномочиями.

**Приоритет:** обязательное.

**Критерий приемки:** пользователь с открытым сеансом после понижения роли или блокировки повторяет ранее разрешенную операцию и получает отказ; данные не изменяются.

**Способ проверки:** AT-11.

**Статус:** сформулировано, реализация запланирована.
