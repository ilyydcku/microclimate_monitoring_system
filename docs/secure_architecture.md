# Защищенная архитектура проекта v0.4

## 1. Основание проектирования

Проект: вариант 17, «Система мониторинга параметров микроклимата».

Версия v0.4 продолжает фактическую v0.3 и опирается на project_description.md, assets.md, access_matrix.md, security_requirements.md, acceptance_scenarios.md, threat_model.md, attacker_model.md и risk_register.md.

В v0.3 фактически реализованы минимальное Python-приложение, загрузка и проверка конфигурации и три автоматических теста. Пользовательский интерфейс, сетевой прием показаний, база данных, полноценная аутентификация и отдельное хранилище аудита еще не реализованы. Поэтому v0.4 не приписывает проекту несуществующие API, протоколы или СУБД.

DFD версии v0.3 сохраняется как исходная модель: E1-E4, P1-P2, D1-D2, точки входа EP-01 - EP-07 и границы доверия TB-01 - TB-04. В v0.4 P1 декомпозируется на архитектурные уровни, P2 уточняется как Audit.

## 2. Выбранные угрозы

В реестре v0.3 семь рисков имеют высокий уровень R=6: RS-01, RS-02, RS-03, RS-08, RS-09, RS-11 и RS-12. Чтобы не выбирать произвольно между угрозами с одинаковой оценкой, в v0.4 включены все семь. Дополнительно выбраны TH-04/RS-04 и TH-06/RS-06, поскольку они непосредственно определяют объектную авторизацию и аудит операции F-05.

| TH-02 Использование чужого сеанса после отзыва | RS-02, R=6 | Требует актуализации полномочий на каждом защищенном запросе |
| TH-03 Изменение сохраненного показания | RS-03, R=6 | Требует сервисного инварианта, исключающего изменение измерения через смену состояния |
| TH-08 Раскрытие секрета через ошибки | RS-08, R=6 | Определяет требования к Configuration, ошибкам и Audit |

## 4. Точки входа

Список из v0.3 не расширяется.

| ID | Точка входа | Проверки |
|---|---|---|
| EP-01 | Вход пользователя | Учетные данные, состояние учетной записи, ограничение попыток; секреты не журналируются |
| EP-02 | Прием показания | Подлинность источника, размер/частота, обязательные поля, конечность чисел, уникальность, свежесть |
| EP-03 | Просмотр показаний и истории | Аутентификация, актуальная роль, разрешение, проверка фильтров |
| EP-04 | Изменение состояния записи | Аутентификация, роль инженера, объектный доступ, валидация, неизменность измерения, аудит |
| EP-05 | Управление учетными записями и ролями | Администратор, допустимая роль, аудит old/new/result |
| EP-06 | Просмотр журнала | Администратор, проверка фильтров и объема выдачи |
| EP-07 | Загрузка конфигурации | Обязательные параметры, допустимый APP_ENV, отсутствие секрета в выводе |

Внутренние вызовы между Validation, Authentication, Authorization, Services, Repository и Audit не являются новыми внешними точками входа.

## 5. Доверительные границы

- TB-01: внешние участники и источники -> приложение. Все данные считаются недоверенными. Пользовательские и административные запросы проходят Validation -> User Authentication -> Authorization -> Services. Поток EP-02 проходит ограничения размера/частоты -> Validation -> Source Authentication -> проверки свежести/повтора -> Services; пользовательская Authorization к источнику не применяется.
- TB-02: приложение -> D1. Доступ только через Repository. Будущая служебная учетная запись хранилища имеет минимальные права. Прямой доступ клиента к D1 не предусматривается.
- TB-03: приложение -> Audit/D2. Событие формирует серверный компонент в фиксированной структуре. Пользователь не передает готовую строку журнала.
- TB-04: среда запуска -> приложение. Конфигурация проверяется app/config.py, секреты не возвращаются пользователю и не передаются в Audit.

## 7. Аутентификация

### Пользователи

Проектируется серверная аутентификация учетной записи с серверным сеансом. После проверки учетных данных клиент хранит только идентификатор сеанса. На каждом защищенном запросе Authentication/Authorization должны учитывать актуальное состояние учетной записи и роль из Repository. Поэтому блокировка или изменение роли действует не позднее следующего защищенного запроса, как требует SEC-17.

Конкретный веб-фреймворк, формат cookie/заголовка и алгоритм хранения пароля в v0.4 не фиксируются, поскольку сетевой стек еще не выбран. Пользовательская аутентификация в коде v0.4 не реализована.

### Источники показаний

Источник не является пользователем приложения и не получает пользовательскую роль. Для EP-02 проектируется отдельный Source Authentication. Сервер должен проверять владение индивидуальным учетным материалом источника; source_id сам по себе не является доказательством подлинности. Проверка связывается с источником и сообщением, а уникальность/время проверяются отдельно по SEC-13.

Конкретный протокол и криптографический формат откладываются до выбора протокола обмена. Это архитектурное решение, а не реализованная защита.

## 8. Авторизация

Роли сохраняются без расширения полномочий: оператор, инженер, администратор. Наследования ролей нет.

app/security/access_control.py реализует явное Role -> Permission. Для сведений об источниках разделены минимальные области просмотра оператора, технической проверки инженера и служебного просмотра администратора. Неизвестная роль получает пустой набор разрешений.

Правила:

- оператор: текущие/исторические показания, поиск/фильтрация, отчеты и только сведения об источнике, необходимые для отображения;
- инженер: те же функции, техническая проверка источников и изменение состояния доступной записи;
- администратор: учетные записи/роли, журнал, административная конфигурация и только служебные сведения об источниках;
- администратор не наследует просмотр показаний и изменение состояния;
- F-05 требует и Permission.CHANGE_RECORD_STATE, и объектного доступа к конкретной записи;
- в учебном прототипе доступные инженеры записаны в неизменяемом поле MonitoringRecord только для демонстрации правила, это не схема будущей БД;
- будущий Repository должен возвращать актуальные роли и объектные назначения.

## 9. Validation

Реализованный app/security/validation.py выполняет техническую валидацию:

- обязательные строки должны быть строками, непустыми после trim и ограниченными по технической длине;
- температура и влажность должны быть конечными числами, bool, NaN и infinity запрещаются;
- для прототипа показания обязательны source_id, temperature, humidity, measured_at;
- для F-05 обязательны record_id и new_status.

Физические допустимые диапазоны температуры, влажности и других параметров не задаются, поскольку исходные материалы их не содержат.

Свежесть и повтор SEC-13 относятся к предметной валидации приема показаний. В v0.4 место проверки определено, но реализация откладывается до появления формата сообщения/протокола.

## 10. Audit

app/audit/audit_logger.py реализует компактный файловый прототип. Каждое событие хранится как одна JSON-строка с occurred_at, actor_id, action, result, object_id, old_value и new_value. Управляющие символы нормализуются, что не позволяет входному переводу строки создать поддельную дополнительную запись.

Интерфейс Audit не принимает пароль, API key, secret key, token или произвольное тело запроса.

Журналироваться должны:

- успешная и неуспешная аутентификация пользователя без секрета;
- отказ подтверждения источника;
- отклонение дубликата/устаревшего сообщения;
- отклонение EP-02 по размеру/частоте;
- отказ авторизации;
- успешная и отклоненная F-05 по SEC-14 с actor, record_id, old/new и result;
- изменение роли по SEC-06 с actor, target, old/new и result;
- ошибки критичных механизмов;
- события SEC-16 после реализации квоты.

Файловый прототип не является реализацией отдельного защищенного D2, квоты 100 МиБ или защиты уже сохраненных событий от изменения.

## 11. Configuration

app/config.py не переписывается. Он уже:

- читает APP_NAME, APP_ENV, APP_SECRET_KEY из окружения/.env;
- допускает development, testing, production;
- требует APP_SECRET_KEY длиной не менее 32 символов;
- возвращает frozen Settings;
- совместно с app/main.py не выводит секрет в стартовом сообщении.

Для v0.4 сохраняются правила: секреты не хранятся в Git, новые секретные параметры не попадают в Audit/ошибки, конфигурация проверяется на TB-04. Новые сетевые секреты в .env.example не добавляются, потому что сетевые механизмы еще не реализованы.

## 12. Сервисный уровень и Repository

Для демонстрации выбрана F-05, потому что с ней связаны TH-03, TH-04, TH-06 и TH-11.

app/services/monitoring_service.py:

1. валидирует record_id и новый статус;
2. проверяет Permission.CHANGE_RECORD_STATE;
3. проверяет объектный доступ actor к записи;
4. при отказе пишет access_denied и не изменяет запись;
5. при разрешении создает новую версию записи, меняя только status;
6. temperature и humidity не входят во входные поля команды и остаются неизменными;
7. пишет old/new и success в Audit.

Полноценный Repository и БД не реализуются. В будущем Repository является единственным путем Services к D1.

## 15. Реализовано и спроектировано

Реализовано в v0.4:

- validation.py;
- access_control.py с тремя существующими ролями и Fail Secure;
- audit_logger.py с нормализацией полей;
- monitoring_service.py для F-05;
- неизменность temperature/humidity при F-05;
- ролевой и объектный отказ;
- аудит успешной и отклоненной F-05;
- новые автоматические тесты.

Только спроектировано:

- пользовательская аутентификация и серверные сеансы;
- подтверждение подлинности источников;
- anti-replay SEC-13;
- rate/size limiting SEC-15;
- реальная модель объектных назначений через Repository;
- СУБД и D1;
- отдельное защищенное D2 и SEC-16;
- пользовательские/административные интерфейсы и сетевой прием.

## 16. Тестирование

Итоговый локальный запуск:

    python -m pytest -q

Результат: 11 passed.

Проверено:

1. корректное показание проходит Validation;
2. пустой source_id отклоняется;
3. оператор не меняет состояние и данные остаются прежними;
