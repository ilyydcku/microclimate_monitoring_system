# Система мониторинга параметров микроклимата

## Назначение

Учебная программная система для мониторинга параметров микроклимата.

## Индивидуальный вариант

Вариант 17: «Система мониторинга параметров микроклимата».

## Основные роли пользователей

- оператор;
- инженер;
- администратор.

## Используемые технологии

- Python;
- Git;
- pytest;
- python-dotenv.

## Запуск проекта

1. Создать виртуальное окружение.
2. Установить зависимости.
3. Создать `.env` на основе `.env.example`.
4. Выполнить `python -m app.main`.

## Тестирование

Выполнить команду `pytest -v`.

## Требования безопасности

- секреты не хранятся в исходном коде;
- конфигурация проверяется при запуске;
- секретные значения не выводятся пользователю;
- зависимости проекта фиксируются.

## Версия v0.3

Подготовлены:

- описание области анализа, фактического и проектируемого состояния и 7 допущений;
- модель 5 типов нарушителей;
- диаграмма потоков данных с 4 внешними сущностями, 2 процессами, 2 хранилищами, 12 потоками и 4 границами доверия;
- перечень точек входа;
- 12 сценариев угроз с покрытием всех шести категорий STRIDE;
- реестр 12 рисков с обоснованием вероятности и последствий;
- подробный план обработки трех приоритетных рисков;
- уточненные требования безопасности SEC-13 - SEC-17 и приемочные сценарии AT-07 - AT-11;
- итоговая таблица прослеживаемости.

Модель угроз относится преимущественно к проектируемой системе. Предполагаемые недостатки не считаются обнаруженными уязвимостями, пока соответствующие компоненты не реализованы и не проверены.

Запланированные защитные меры не считаются действующими, а прогнозируемое снижение риска требует последующего подтверждения тестами.

## Версия v0.4

Спроектирована защищенная архитектура на основе фактической v0.3 и модели угроз без изменения предыдущих версий.

Подготовлены и реализованы:

- архитектурные группы Interface, Validation, Authentication, Authorization, Services, Repository, Storage, Audit и Configuration;
- сохранение точек входа EP-01 - EP-07 и доверительных границ TB-01 - TB-04 из v0.3;
- отдельная модель аутентификации пользователей и источников показаний;
- явная модель ролей и разрешений для оператора, инженера и администратора;
- прототипы `validation.py`, `access_control.py`, `audit_logger.py`;
- сервисный прототип изменения состояния записи без возможности менять сохраненные значения измерения;
- структурированный аудит успешной и отклоненной операции;
- Mermaid-схема и матрица «угроза - защита» в `docs/secure_architecture.md`;
- автоматические проверки новых механизмов.

Сетевой интерфейс, БД, серверные пользовательские сеансы, подтверждение подлинности источников, anti-replay и rate limiting остаются архитектурными решениями и не обозначаются как реализованные механизмы.

## Версия v0.5

Практическая работа № 5: безопасная обработка пользовательского ввода.

- `app/validation.py`: проверка JSON, UTF-8, ограничения размера 8192 байт, нормализация Unicode NFC, проверка обязательных полей, типов, диапазонов, IP-адресов, запрет повторных ключей и неизвестных полей;
- `main.py`: безопасная точка входа для JSON-заявки, которая передает в обработку только проверенный объект;
- вариант 17: разрешен только логический идентификатор вложения `log`, произвольные файловые пути отклоняются;
- `docs/validation_policy.md`: политика проверки входных данных;
- `tests/test_validation.py`: положительные и отрицательные автоматизированные проверки;
- `example.json`: корректный демонстрационный запрос;
- `VERSION`: номер версии `0.5`.

Запуск примера в Windows CMD из корня проекта:

```cmd
python main.py < example.json
```

Проверки:

```cmd
python -m unittest discover -s tests -v
python -m pytest -q
```

Предыдущие модули мониторинга, авторизации и аудита сохранены. Новая учебная точка входа не является сетевым API или реализацией приема данных от реальных датчиков.

## Версия v0.6

Практическая работа № 6: предотвращение SQL-инъекций, обхода каталогов и
командных инъекций, безопасная работа с файлами.

- `app/repositories/requests.py`: параметризованные SQLite-операции с
  проверенными объектами `ValidatedRequest`, проверка типов и разрешённая
  сортировка; удаление записей с вложениями запрещено;
- `app/storage/files.py`: проверка категории и содержимого, ограничение 1 МиБ,
  случайный ID вместо пользовательского пути, исключающее создание файла,
  ограниченное чтение;
- `app/services/request_service.py`: интеграция валидации, SQLite и FileStore с
  удалением нового файла при ошибке записи в БД;
- `app/security/safe_command.py`: запуск фиксированной программы с
  `shell=False`, отдельными аргументами и тайм-аутом;
- `demo_v06.py`: демонстрационный запуск цепочки v0.5 -> v0.6;
- `tests/test_v06.py`: позитивные/негативные тесты, включая индивидуальный
  вариант 17 - дополнительные проверки UTF-8 журналов;
- `docs/v06_security_operations.md`: схема, правила и остаточные риски.

Входная валидация варианта 17 по-прежнему разрешает только `attachment_key=log`.
Общее файловое хранилище поддерживает и другие категории для выполнения
задания, но входной контракт `app/validation.py` не расширялся.

Запуск из корня проекта:

```cmd
python demo_v06.py
python -m unittest discover -s tests -p "test_v06.py" -v
python -m pytest -q
```

SQLite-база в `data/` и файлы в `private_data/` создаются локально и не
добавляются в Git. Реальная база показаний температуры и влажности,
сетевой API и полноценная защита содержимого PDF/PNG этой работой не реализуются.

## Версия v0.7

Практическая работа № 7: реализация безопасной парольной аутентификации и
серверных сеансов. Предыдущие модули v0.1–v0.6 сохранены без изменений.

- `app/auth.py`: регистрация в SQLite, проверка пароля, ограничение попыток,
  отзыв и проверка сеансов, восстановление доступа по одноразовому коду;
- парольная политика: NFC, 15–128 символов для новых паролей, проверка учебного
  списка слабых значений, индивидуальная соль 16 байт, PBKDF2-HMAC-SHA-256
  с 600 000 итераций в обычной конфигурации;
- временная блокировка: пять последовательных ошибок, 60 секунд;
- сеансовый токен: `secrets.token_urlsafe(32)`; в SQLite хранится только SHA-256
  токена, срок бездействия 15 минут и абсолютный срок 60 минут;
- резервный код: генерируется при регистрации, в базе только SHA-256;
  успешное восстановление заменяет код и отзывает все старые сеансы;
- `demo_v07.py`: локальная демонстрация регистрации, входа, проверки и выхода;
- `tests/test_v07.py`: 15 обязательных тестов методички, три сценария
  индивидуального варианта №17 и дополнительные проверки;
- `docs/v07_authentication.md`: архитектура, исследование Brute Force и
  Password Spraying, результаты и остаточные риски.

Индивидуальный вариант №17: **исследование различий Brute Force и Password
Spraying**. Проверено, что пять неудач в одной учётной записи приводят к
блокировке, но распределение одной попытки по нескольким учётным записям не
достигает порога на каждом аккаунте. Это остаточный риск данной учебной схемы,
а не заявление о защите от распределённого подбора.

Запуск из корня проекта (Windows PowerShell):

```powershell
.\.venv\Scripts\python.exe demo_v07.py
.\.venv\Scripts\python.exe -m unittest discover -s tests -p "test_v07.py" -v
.\.venv\Scripts\python.exe -m unittest discover -s tests -v
.\.venv\Scripts\python.exe -m pytest -q
```

Только изолированные функциональные тесты используют `rounds=1000`, чтобы
сократить время выполнения. Отдельный тест проверяет регистрацию, вход и
восстановление с обычным значением 600 000. Файл `data/users.sqlite3`,
сеансовые токены и резервные коды не публикуются в Git.
